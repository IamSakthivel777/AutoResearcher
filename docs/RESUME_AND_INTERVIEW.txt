2. PROJECT EXPLANATION FOR INTERVIEWS
-------------------------------------

30-second explanation
AutoResearcher is a Python package that takes a question, creates a research
plan, gathers web evidence in parallel, checks citations, and generates a
professional Word report. It supports multiple LLM providers, a CLI and Python
API, weather and trip planning, multilingual highlights, and attributed images.

One-minute explanation
The system uses LangGraph to coordinate a planner, several parallel workers,
an evidence critic, and a report synthesizer. Workers use controlled tools for
web search, page fetching, weather, places, budgets, and travel estimates.
Claims are connected to source IDs, and the critic rejects missing citations.
The final report is rendered deterministically with python-docx, rather than
asking an LLM to write DOCX bytes. Users install the package with pip, supply
an API key through environment variables, and call AutoResearcher.run() or the
autoresearcher command-line tool.

Problem solved
People need a structured research report, but manually searching sources,
checking evidence, writing a document, and adding visuals takes time. The
package automates the workflow while keeping sources visible in the report.

Main user flow
1. User gives a question and an output DOCX path.
2. The clarifier extracts useful scope such as location, duration, budget, and
   a complete travel date when one is explicitly provided.
3. The planner produces bounded research tasks.
4. Parallel workers gather evidence through typed tools.
5. The critic checks evidence and can request focused revisions.
6. The synthesizer writes a report specification with source references.
7. The DOCX renderer creates the final document, sources section, images, and
   translated highlights.


3. ARCHITECTURE TO DRAW OR EXPLAIN
---------------------------------

Question
  -> Clarifier
  -> Planner
  -> Parallel workers (web, weather, places, transport, budget, retrieval)
  -> Evidence critic
  -> Synthesizer / image planner / language highlights
  -> Deterministic DOCX renderer
  -> Cited .docx report

Key design choices
* LangGraph controls state, fan-out, fan-in, and bounded research loops.
* Pydantic validates configuration, plans, tasks, sources, claims, and reports.
* LLMs decide plans and summaries; deterministic Python code handles file
  generation, validation, calculations, and external tool access.
* Every final factual claim must have source IDs; source URLs come from tools,
  not directly from an LLM response.
* Failures are warnings when safe to continue, so a partial report can still
  be useful while clearly showing limitations.

5. LIKELY INTERVIEW QUESTIONS AND ANSWER GUIDANCE
-------------------------------------------------

Q1. What is AutoResearcher?
A. It is a Python package that turns a natural-language research question into
   a source-grounded DOCX report using a multi-agent workflow.

Q2. Why did you use a multi-agent design?
A. Research has separable tasks: planning, weather, places, web evidence,
   critique, and writing. Parallel workers reduce waiting time and allow each
   task to use focused tools. A final critic and synthesizer combine the work.

Q3. Why LangGraph instead of one long LLM prompt?
A. LangGraph provides explicit state, parallel fan-out/fan-in, retries and
   limits, clear node boundaries, and easier testing. A single prompt is less
   controllable and makes evidence handling harder.

Q4. What is the graph state?
A. It stores the question, plan, findings, sources, warnings, token usage,
   revision-loop count, output path, and final report specification.

Q5. How do parallel workers work?
A. The planner creates tasks. LangGraph Send fan-out dispatches tasks to
   workers, then reducers combine findings and deduplicate sources at fan-in.

Q6. How do you prevent unlimited cost or runtime?
A. The constructor has max_subagents, max_critic_loops, max_tool_calls,
   token_budget, task_timeout_seconds, and llm_timeout_seconds. The graph also
   has a recursion limit.

Q7. How do you reduce hallucinations?
A. The design requires source IDs on final claims. URLs are created by trusted
   tools, not the model. A deterministic critic rejects missing citations, and
   the final document includes a source list.

Q8. Does this guarantee that every source is correct?
A. No. Citation grounding improves traceability, but sources may be incomplete,
   stale, biased, or wrong. Users must review reports for high-stakes decisions.

Q9. Why use Pydantic?
A. Pydantic validates inputs and structured data at each boundary: settings,
   tasks, claims, sources, report blocks, and events. It prevents malformed
   data from silently reaching the renderer.

Q10. How do you handle structured LLM output?
A. The planner uses Pydantic schemas and the provider's structured-output or
    function-calling support. The code uses a compatible method for OpenAI so
    rich schemas do not fail at runtime.

Q11. Why deterministic DOCX rendering?
A. LLMs are good at text but not reliable at producing binary Office files.
    A validated report specification is passed to python-docx, which makes
    layout, citations, headings, and images repeatable.

Q12. How are citations represented?
A. Sources have stable IDs such as S1. Claims reference one or more source IDs.
    The report renderer validates references before writing the document.

Q13. How do you handle tool failures?
A. Expected tool failures become warnings with task context when the graph can
    safely continue. The report can use available evidence instead of failing
    entirely, but it exposes the limitation to the user.

Q14. Which search provider do you use?
A. Tavily is used when TAVILY_API_KEY is present. DuckDuckGo is the fallback,
    so basic research works without an additional search API key.

Q15. How do you handle weather?
A. The weather tool uses Open-Meteo geocoding and forecast data. A full user
    travel date is parsed only when explicitly given. Outside the forecast
    window, the report does not fabricate exact daily weather.

Q16. Why is date parsing important?
A. A date shown in a report can be mistaken for an itinerary date. The design
    distinguishes the report-generation date from a user-provided travel date.

Q17. How are images added safely?
A. The image planner chooses named places, searches Wikimedia Commons, checks
    usable image formats, embeds local copies, and adds creator/license/source
    attribution to the report.

Q18. Why use Wikimedia Commons?
A. It provides a practical source of openly licensed media and metadata needed
    for attribution. The report records the source and license information.

Q19. How does multilingual support work?
A. The English report remains the primary evidence base. A writer model creates
    Tamil, Hindi, Telugu, and Malayalam source-linked highlights, preserving
    references instead of inventing independent translated facts.

Q20. What LLM providers are supported?
A. OpenAI, Anthropic, and Gemini. Each role can route to a provider or a
    provider/model combination, and the system can fall back to another
    configured provider with a warning.

Q21. How do you protect API keys?
A. Keys come from constructor arguments, environment variables, or .env files.
    Pydantic SecretStr hides them in representations and validation errors. The
    repository ignores .env files and examples never print keys.

Q22. Why are environment variables preferred over hard-coding keys?
A. They separate secrets from code, work with deployment secret managers, and
    reduce the risk of committing credentials to GitHub.

Q23. What is the difference between run() and arun()?
A. run() is the synchronous API for scripts. arun() is for async applications
    such as FastAPI or Jupyter. Calling run() inside an active event loop raises
    an intentional error.

Q24. How can an application show progress?
A. stream() yields typed events such as PlanCreated, TaskStarted, TaskFinished,
    CriticVerdict, and ReportWritten.

Q25. How did you test the project?
A. The normal pytest suite uses fake LLMs and mocked network calls, so tests are
    offline and do not spend API credits. Ruff checks style and common errors;
    mypy checks strict types; Twine validates package metadata.

Q26. How do you test a real provider?
A. A separate opt-in live example reads OPENAI_API_KEY and runs a real report.
    It is not part of normal offline tests because it costs money and needs
    network access.

Q27. What caused the LangChain dependency conflict and how did you fix it?
A. Older integration constraints required LangChain Core 0.3 and LangGraph 0.6,
    which conflicted with an application's LangChain 1.x. The package was
    migrated to LangChain/LangGraph 1.x-compatible provider integrations and
    verified with pip check and a clean environment containing LangChain 1.4.2.

Q28. What is a wheel?
A. A wheel (.whl) is the standard built Python distribution that pip installs.
    The project also builds a source archive (.tar.gz). Both are validated before
    upload with twine check.

Q29. Why must the PyPI version change for every release?
A. PyPI release files are immutable. If version 0.1.1 is uploaded, a corrected
    release must use a new version such as 0.1.2.

Q30. What is the difference between the package name and import name?
A. Users install `autoresearcher-ai`, but import it as
    `from autoresearcher import AutoResearcher`. PyPI distribution and Python
    import names are allowed to differ.

Q31. What would you improve next?
A. Add persistent storage and job queues, a web/API layer, stronger source
    ranking, evaluation datasets, user-selectable report templates, caching,
    observability, and human approval before final report delivery.

Q32. What are the current limitations?
A. Search results can be incomplete, images are best-effort, model output can
    vary, external APIs can rate-limit, and the report should not be used as the
    sole source for high-stakes decisions.

Q33. How would you deploy this in production?
A. Package it in a container or virtual environment, inject secrets through a
    secret manager, queue jobs in background workers, store outputs in managed
    object storage, add logging/metrics, set provider spend limits, and keep
    the web request separate from long-running report generation.

Q34. How would you improve retrieval quality?
A. Add domain-specific search providers, source-quality scoring, duplicate
    detection, reranking, claim-source entailment checks, and evaluation sets
    that measure citation precision and report usefulness.

Q35. How would you explain your contribution confidently?
A. Describe the problem, the architecture, one difficult bug you solved such as
   dependency compatibility or DOCX image handling, how you tested it, and
   what trade-off you made. Be specific and truthful.


6. ADVANCED CROSS-QUESTIONS: SOURCES, SPEED, MEMORY, AND SCALE
---------------------------------------------------------------

Q36. How many tools are in the current package?
A. There are 12 exported application tools: web search, page fetching, place
   search, weather forecast, image search, image download, travel-time
   estimation, budget estimation, itinerary building, local embed-and-store,
   local retrieval, and DOCX rendering.

Q37. Which tools call external services?
A. Web search uses Tavily or DuckDuckGo, place search uses OpenStreetMap,
   weather uses Open-Meteo, and image search/download uses Wikimedia Commons.
   Budget, travel-time, itinerary, local memory, and DOCX rendering run locally.

Q38. Are all sources trusted automatically?
A. No. The current package provides source traceability, not a guarantee of
   truth. It records URLs, source titles, retrieval time, and citations. Users
   must still review high-stakes facts and time-sensitive information.

Q39. How would you improve source trust?
A. Add a source policy: prefer official government, provider, academic, and
   first-party domains; allowlist trusted domains per topic; fetch full pages;
   require independent corroboration for important claims; check source date;
   flag low-quality domains; and preserve evidence excerpts for reviewer audit.

Q40. How do you defend against prompt injection in web pages?
A. Treat web content as untrusted data, not instructions. Keep tool results
   separated from system prompts, strip unsafe markup, prohibit tools from
   executing page instructions, use URL allow/deny policies, and require a
   human review step for sensitive output.

Q41. How fast is one report?
A. There is no fixed benchmark because latency depends on provider response,
   search services, task count, images, and document size. The system uses
   parallel worker branches to reduce wall-clock time, but external LLM calls
   are normally the largest source of latency.

Q42. What timeouts and limits are configured?
A. By default, each worker task has a 60-second timeout and each LLM request
   has a 180-second timeout. A run defaults to 8 subagents, and configuration
   permits 1 to 64 subagents. These are safeguards, not a speed guarantee.

Q43. Does max_subagents=8 mean eight users can use it at once?
A. No. It means one report can execute up to eight research-worker tasks in
   parallel. It is not a global server concurrency limit and it does not manage
   simultaneous users across processes or machines.

Q44. Can the current package support 1,000 users at the same time?
A. Not as a standalone library. It has no multi-tenant API server, job queue,
   database, distributed rate limiter, persistent shared memory, or capacity
   controls. It must be wrapped in production infrastructure first.

Q45. What would a 1,000-user architecture look like?
A. Put an authenticated API in front of a durable job queue. Store job state in
   PostgreSQL or Redis, run horizontally scaled worker containers, store DOCX
   files in object storage, enforce per-user quotas and provider rate limits,
   add a global concurrency semaphore, and monitor queue depth, latency, error
   rate, and token cost. Scale reports gradually after load tests.

Q46. How does memory work today?
A. The current Phase 2 memory is a small in-process dictionary of deterministic
   128-dimensional hashed bag-of-words vectors. It is protected by a thread
   lock and grouped by namespace. It disappears when the Python process exits,
   is not shared across servers, and is not a production persistent vector DB.

Q47. Is the current memory suitable for multiple users?
A. Only for small, controlled in-process use. A default namespace could mix
   users if an application does not choose isolated namespaces. Production needs
   a persistent store with tenant IDs, access controls, retention policy,
   encryption, deletion support, and a proper vector database or retrieval
   service.

Q48. How much memory can the local index hold?
A. Each embed-and-store call accepts up to 1,000 texts and retrieval returns up
   to 50 results, but there is no global memory cap, disk persistence, eviction,
   or distributed coordination. That is why it is deliberately described as a
   Phase 2 local index rather than production memory.

Q49. What load test would you perform before claiming scale?
A. Use realistic report questions and provider quotas. Measure p50/p95 latency,
   completed jobs per minute, queue wait time, error rate, CPU/RAM use, source
   API failures, DOCX generation time, and token cost at increasing concurrency.
   Define a safe concurrency limit from observed data, not a guess.

Q50. What happens if OpenAI rate-limits requests?
A. The application should retry only retryable errors with exponential backoff,
   respect Retry-After headers, limit concurrent calls, queue excess jobs, and
   show users a clear queued or delayed status. Provider fallback can help only
   when another configured provider has compatible capacity and cost controls.

Q51. What metrics would you monitor?
A. Job success/failure rate, end-to-end latency, node latency, queue depth,
   provider errors/rate limits, tool failures, source count, citation coverage,
   token usage, cost per report, memory usage, and image/download failures.

Q52. What is the honest production status of the project?
A. It is a tested package and a strong prototype for research-report generation.
   It is not yet a complete multi-tenant SaaS platform. Production scale requires
   infrastructure, security review, load testing, persistent storage, and
   operational monitoring.
